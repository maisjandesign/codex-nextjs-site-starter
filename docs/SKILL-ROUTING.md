# Required skill routing

## Startup contract

This project includes 27 local skills: ten site-* workflow skills, the eleven original skills requested by the user, and six official GSAP skills. They are actual skill files, not names that require a future installation. Resolve project-local .agents/skills/<name>/SKILL.md first. Read this document together with AGENTS.md and WORKFLOW.md before implementation, then load the skills needed for the current stage. Read supporting references when their subject is needed; do not load every reference or run every audit at startup.

At the beginning of each new site:

1. Verify that the eleven entrypoints listed below are present. Preserve the original installations; project-local copies are the reproducible snapshot for this template. If skill discovery has not refreshed, read their exact paths directly or open a new task in the extracted project.
2. Read the screenshot brief and the current phase. Load better-layout, better-typography, better-colors, better-ui, better-writing, and better-accessibility for the initial implementation conventions. Use design-taste-frontend's reference/brief reasoning for marketing pages and portfolios; respect its exclusion of dense product interfaces.
3. Read docs/MOTION-LIBRARIES.md, inspect suitable live references, and use the installed GSAP engine. Apply site-assets and docs/IMAGE-ASSETS.md to generate needed raster imagery during desktop work. Define a short desktop motion plan using animate, implement effects with each section/control, and perform the required desktop browser motion review in docs/MOTION-LIBRARIES.md. Do not wait for reminders about motion, hover, or needed generated images. Use animation-vocabulary when an effect needs a precise name and apple-design when fluid interaction/gesture principles are relevant. Neither is a reason to add new effects or restyle the reference.
4. Record skills loaded, their purpose, and deferred/not-applicable work in docs/BRIEF.md. Start the desktop promptly; this routing step is not a separate report, approval gate, or full interface audit.

If an entrypoint is missing in a modified archive, check available project/global skill locations and report the specific gap. Continue independent work using the available site-* rules without claiming the missing skill ran. If the user explicitly requires the unavailable skill itself for dependent work, leave that work pending until it is available. Do not silently substitute interface-design for better-interface; they are different skills.

## Project rules that resolve skill conflicts

These are the user's project requirements applied to the copied skills. Preserve the original files and use this integration policy; do not silently edit installed skills or treat one skill's opinion as permission to override the brief.

- Delivery: early desktop preview, then polished desktop plus its populated Storybook catalog and token editor, explicit desktop acceptance, mobile decision, authorized adaptation, and only then the full browser regression suite and cross-browser/multi-viewport matrix. Requirements such as audit-first, final pre-flight before any output, or narrow-width checks must be applied at the correct stage. Desktop motion/interaction browser review is required earlier under docs/MOTION-LIBRARIES.md; focused automated reproduction and immediate defect fixes are allowed. The delayed QA rule must never defer this desktop readiness requirement.
- Supplied designs: follow AGENTS.md, Implementing supplied designs. Screenshots and mockups define the composition, section inventory/order, hierarchy, grid, alignment, image placement, character, palette, and flows. Better layout/typography/UI and design-taste-frontend normalize local inconsistencies through shared roles; they do not authorize recomposition or structural changes. Preserve intentional differences and uncertain composition. Keep structural suggestions separate; implement them only on an explicit user request or approval. This rule overrides conflicting aesthetic bans, hero formulas, font defaults, and layout recommendations in bundled skills. Preserve accepted desktop during adaptation and QA. Generate necessary high-resolution imagery under IMAGE-ASSETS.md while retaining its placement and layout role.
- Stack: retain Next.js App Router, TypeScript, shared components, and the established plain CSS/token pipeline. Tailwind/UI-kit/install suggestions are conditional alternatives, not instructions to migrate this starter. animate's references to pick-ui-library, review-animations, improve-animations, and find-animation-opportunities name separate skills that are not bundled or required to run this workflow. For existing component work, use the site's primitives and accessibility rules; do not silently install a second kit.
- Documentation: use actual Storybook under DOCUMENTATION-TEMPLATE.md, retaining its native hierarchy, Docs, Controls, and light interface. Project styles and motion affect the specimens; none of these skills may reskin the shell for a new project. Keep docs/project typography and token scopes separately verified.
- Accessibility/theme: retain native semantics, keyboard operation, focus, labels, and reduced-motion fallbacks. Never automatically darken the page, invent a dark palette, add decorative scrims, or apply brightness filters. apple-design's material/dimming guidance applies only to a requested interaction consistent with the reference. Report contrast conflicts and propose targeted changes; do not recolor the site without the required project decision.
- Values: project token roles are authoritative. Do not let better-ui's press scale, apple-design's spring/press examples, and animate's timing tables create three competing systems. Reuse one shared token per role, or intentionally revise that role once. Source dimensions/durations are integers; unitless scale, opacity, line-height, easing, and physics coefficients may be fractional. Library seconds can be derived from integer millisecond tokens. Never round responsive browser geometry merely to enforce integer source values.
- Motion: provide the requested meaningful block entrances and interaction feedback during desktop implementation. Do not read a rule about skipping initial animation as a ban on intentional section entrances. Avoid repeated/high-frequency decorative movement, keep fast keyboard actions responsive, and preserve static feedback. Reduced motion may use instant changes; it must never hide content or force movement because a recipe does. Use GSAP as the installed engine and follow docs/MOTION-LIBRARIES.md for project-specific library effects. The older cheapest-tool/CSS recipe defaults do not authorize delivering only generic CSS fades. Keep simple CSS state feedback and match actual installed APIs.
- Scope/verification: applying principles during a build is different from conducting a standalone audit. The site-building request authorizes implementing ordinary in-scope improvements; it does not turn a later review-only task into a code-edit request. A missing domain/check stays Not reviewed / Not verified. Never claim a holistic pass based on reading skill names or a previous demo result.

## Required motion coverage

Follow AGENTS.md, Mandatory desktop motion: header, hero, shared buttons/button-links and each major section must have implemented, observed motion before desktop completion. Color-only hover, press-only scale, an installed library or an isolated catalog demo does not satisfy it. Implement motion alongside the supplied layout; preserve its composition. Record actual role-by-role browser evidence and unverified states in BRIEF.md. Reduced-motion fallbacks remain required; the full cross-browser/viewport matrix stays in final QA.

## Coordinated sequence implementation

Use [MOTION-SEQUENCES.md](MOTION-SEQUENCES.md) for the shared opening/section API and focused behavior checks. Implement header and hero as one planned opening; each major section owns its heading/content sequence. The same implementation must appear in the live catalog. First-screen parallax is excluded: do not add it as a default or inherit it from a reference sandbox. Desktop motion remains required, with full browser/viewport QA at its existing later stage.
