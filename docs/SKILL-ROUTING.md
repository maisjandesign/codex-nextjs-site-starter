## Startup contract

This project includes 21 local skills: six site-* workflow skills, eight design skills, six official GSAP skills, and Graft. They are actual skill files, not names that require a future installation. Resolve project-local .agents/skills/<name>/SKILL.md first. Read this document together with AGENTS.md and WORKFLOW.md before implementation, then load the skills needed for the current stage. Read supporting references when their subject is needed; do not load every reference or run every audit at startup.

At the beginning of each new site, first run `npm run setup` under [STARTUP.md](STARTUP.md). It installs/restores missing required local skills and runtime dependencies and skips valid installed copies. Complete this before implementation; Graft requires its CLI as well as SKILL.md.

1. For coding tasks, read [GRAFT.md](GRAFT.md) and [Graft](../.agents/skills/graft/SKILL.md), build/map the code after dependency installation, and use targeted queries before shared changes. Confirm actual source, use rg for text search, and check freshness after edits. No global initialization or deep/LLM processing is required. Verify that the eight design entrypoints listed below are present. Preserve the original installations; project-local copies are the reproducible snapshot for this template. If skill discovery has not refreshed, read their exact paths directly or open a new task in the extracted project.
2. Read the screenshot brief and the current phase. Load better-layout, better-typography, better-colors, better-ui, better-writing, and better-accessibility for the initial implementation conventions. Use design-taste-frontend's reference/brief reasoning for marketing pages and portfolios; respect its exclusion of dense product interfaces.
3. Read docs/MOTION-DEFAULTS.md and implement the three GSAP defaults. First classify the source under docs/DESIGN-SOURCE.md. Apply site-assets and docs/IMAGE-ASSETS.md to export original Figma images/SVG assets or generate imagery for flat regions during desktop work. Use the available Figma integration and its required skills for actual selection inspection/export; those tools are environment-dependent, not bundled by this template. Define a short desktop motion plan using site-motion and the relevant GSAP skills, implement effects with each section/control, and perform the required desktop browser motion review in docs/MOTION-DEFAULTS.md. Do not wait for reminders about motion, hover, or needed generated images.
4. Record skills loaded, their purpose, and deferred/not-applicable work in docs/BRIEF.md. Start the desktop promptly; this routing step is not a separate report, approval gate, or full interface audit.

If an entrypoint or supporting file is missing, run setup to restore the pinned project copy. If restoration or dependency installation fails, follow STARTUP.md, report the actual blocker and continue only independent work without claiming startup complete. If the user explicitly requires the unavailable skill itself for dependent work, leave that work pending until it is available. Do not silently substitute interface-design for better-interface; they are different skills.

## Project rules that resolve skill conflicts

These are the user's project requirements applied to the copied skills. Use this integration policy. User-requested motion adaptations are recorded in SKILL-INVENTORY.json; global skill installations are unchanged.

- Code orientation: follow GRAFT.md for the preserved Graft skill. Use its local structural graph for relevant coding tasks; source remains ground truth. Its blanket instructions to replace text search, trust results without verification, set up global hooks or report estimated savings do not apply. No LLM/deep or external upload is part of the default workflow.
- Delivery: early desktop preview, then polished desktop plus its populated Storybook catalog and token editor, explicit desktop acceptance, mobile decision, authorized adaptation, and only then the full browser regression suite and cross-browser/multi-viewport matrix. Requirements such as audit-first, final pre-flight before any output, or narrow-width checks must be applied at the correct stage. Desktop motion/interaction browser review is required earlier under docs/MOTION-DEFAULTS.md; focused automated reproduction and immediate defect fixes are allowed. The delayed QA rule must never defer this desktop readiness requirement.
- Supplied designs: follow AGENTS.md, Implementing supplied designs. Screenshots and mockups define the composition, section inventory/order, hierarchy, grid, alignment, image placement, character, palette, and flows. Better layout/typography/UI and design-taste-frontend normalize local inconsistencies through shared roles; they do not authorize recomposition or structural changes. Preserve intentional differences and uncertain composition. Keep structural suggestions separate; implement them only on an explicit user request or approval. This rule overrides conflicting aesthetic bans, hero formulas, font defaults, and layout recommendations in bundled skills. Preserve accepted desktop during adaptation and QA. Inspect structured/flat/mixed sources under DESIGN-SOURCE.md; export original Figma assets or generate imagery for flat regions under IMAGE-ASSETS.md while retaining placement and layout role.
- Stack: retain Next.js App Router, TypeScript, shared components, and the established plain CSS/token pipeline. Tailwind/UI-kit/install suggestions are conditional alternatives, not instructions to migrate this starter. For existing component work, use the site's primitives and accessibility rules; do not silently install a second kit.
- Documentation: use actual Storybook under DOCUMENTATION-TEMPLATE.md, retaining its native hierarchy, Docs, Controls, and light interface. Project styles and motion affect the specimens; none of these skills may reskin the shell for a new project. Keep docs/project typography and token scopes separately verified.
- Accessibility/theme: retain native semantics, keyboard operation, focus, labels, and reduced-motion fallbacks. Never automatically darken the page, invent a dark palette, add decorative scrims, or apply brightness filters. Report contrast conflicts and propose targeted changes; do not recolor the site without the required project decision.
- Values: project token roles are authoritative. Do not let skill examples create a second system of timing, spacing or interaction values. Reuse one shared token per role, or intentionally revise that role once. Source dimensions/durations are integers; unitless scale, opacity, line-height and easing may be fractional. Library seconds can be derived from integer millisecond tokens. Never round responsive browser geometry merely to enforce integer source values.
- Motion: follow only MOTION-DEFAULTS.md for upward masked entrances, GSAP object hovers and ScrollSmoother. Upstream examples are API reference for these three families only. They must not introduce additional effects, profiles, engines or research tasks.

- Scope/verification: applying principles during a build is different from conducting a standalone audit. The site-building request authorizes implementing ordinary in-scope improvements; it does not turn a later review-only task into a code-edit request. A missing domain/check stays Not reviewed / Not verified. Never claim a holistic pass based on reading skill names or a previous demo result.
