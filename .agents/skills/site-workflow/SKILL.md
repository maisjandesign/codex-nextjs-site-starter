# site-workflow

Before coding or launching a new project, read docs/STARTUP.md and run npm run setup. It checks all required local skills, restores missing files and installs missing project dependencies including the Graft CLI. Already installed skills/packages are skipped; do not overwrite customizations or treat SKILL.md as an installed executable. If setup fails, follow STARTUP.md for permitted network/permission recovery and rerun it. Do not silently replace required tooling with a stale node_modules folder or declare startup complete.

After successful setup, read docs/GRAFT.md and .agents/skills/graft/SKILL.md, then run npm run graft:build and npm run graft:map. Query relevant symbols/callers before shared implementation changes and verify actual source. Use rg for text search. If installation remains blocked, record the error and continue only independent work; source inspection is not a successful Graft setup. No global init/hooks or deep/LLM setup is required.

Read AGENTS.md, docs/DESIGN-SYSTEM.md, docs/DESIGN-SOURCE.md, docs/BRIEF.md, docs/SKILL-ROUTING.md, and docs/WORKFLOW.md. First inspect and classify the actual source as structured Figma, flat image or mixed. Export originals for structured regions and generate replacement imagery for flat reference regions. Preserve useful text/assets; do not infer structure from layer count. Record evidence and access gaps, then implement promptly. Follow the supplied-design implementation rules in AGENTS.md. Preserve section inventory/order, content hierarchy, layout, grid, alignment, image placement, visual character, palette, and user flows. Normalize only isolated inconsistencies through shared semantic tokens and components, preserving intentional role differences. When intent is uncertain, keep the supplied composition. Structural suggestions stay separate and require an explicit user request or approval before implementation. Before desktop review, record the normalized inconsistencies and shared rules applied. Once desktop is accepted, preserve that baseline during mobile adaptation and QA unless the user requests a redesign; a new image alone does not reset approval. Record uncertain assets or measurements, then implement promptly.

Read docs/MOTION-DEFAULTS.md and docs/IMAGE-ASSETS.md during startup. Implement GSAP ScrollSmoother, masked entrances and expressive GSAP button/button-link hovers during desktop work, without another animation request; record their observed behavior before acceptance. Use docs/MOTION-DEFAULTS.md as the single motion contract; only the three effects in that contract are in scope. Use site-assets to export original Figma images/SVG assets or generate imagery for flat regions according to source classification; do not use flattened UI crops as production photos. Show a meaningful desktop preview early. Start npm run storybook alongside npm run dev. Build the pages, real component stories, and /design-system token lab together using site-tokens, better-layout, better-typography, better-ui, and site-motion. Use docs/DOCUMENTATION-TEMPLATE.md for the native Storybook hierarchy, Autodocs, Controls, and per-component state stories; fill it with project-specific content and isolate its appearance from project token edits. The first preview may be rough; desktop completion includes polished interaction/entrance motion, consistent shared roles, and the synchronized catalog with a working token editor and source persistence. See docs/DESIGN-SYSTEM.md; the included Design tools panel covers registered desktop/shared colors, sizes, typography and spacing; the GSAP controls edit the retained effects. Storybook is included.

Apply desktop revisions until explicit acceptance. Then ask about mobile and wait unless that exact next step was already authorized. If declined, deliver desktop and defer mobile and combined QA. If authorized, use site-responsive while preserving the approved desktop.

Use site-qa only when approved desktop and authorized mobile are ready with known requested changes complete. Desktop motion/interaction browser review is required earlier under docs/MOTION-DEFAULTS.md; implement and inspect effects with each section/control. Focused automated reproduction, runtime fixes, token input validation, and user revisions remain allowed. Keep readiness pending for required unverified motion states, and show early drafts with clear limitations. Use better-accessibility to preserve usability without automatic recoloring or dimming.

Record readiness, approval evidence, normalized inconsistencies, and shared rules in docs/BRIEF.md. The eight design skills are bundled locally and must be routed through docs/SKILL-ROUTING.md. Read the six Better domain skills during initial implementation, apply design-taste-frontend when the surface fits, and use site-motion with the relevant official GSAP skills during desktop motion work. Explicitly invoke better-interface quick before desktop completion and full during stage 4. Its verdict does not replace user approval. No external plugin is required. Do not add approval gates or publish without a publication request.
